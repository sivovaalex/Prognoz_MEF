# Назначение документа

Этот документ определяет высокоуровневые требования и порядок разработки доработки информационной системы «Конструктор форм» (ГАС «Управление» МО) — подраздела «Пояснительная записка» (ПЗ) блока «Муниципальный прогноз» модуля «Прогноз СЭР МО». Документ также определяет критерии приёмки результатов работ для объективной оценки соответствия системы утверждённым требованиям.

Данная доработка должна решать следующие задачи:

1. Сбор от органов местного самоуправления (ОМСУ) пояснительных (текстовых) данных по показателям блока «Муниципальный прогноз»;
2. Поячеечное согласование данных ОМСУ отраслевыми ЦИО, включая возврат на доработку с обязательным комментарием;
3. Формирование итоговых (выходных) таблиц пояснительной записки — итогового документа за текущий отчётный год и архивные годы (последние 15 лет);
4. Ведение истории операций и уведомление участников процесса.

**Обзор проекта/доработки и предпосылки:**

Модуль «Прогноз СЭР МО» системы «Конструктор форм» содержит блок «Муниципальный прогноз» с числовыми прогнозами показателей по муниципальным образованиям. Помимо числовых значений, прогноз требует пояснительного текста: по каждому показателю ОМСУ поясняет причины изменений, тенденции и планы (например, «Причины увеличения/снижения промышленного производства», «Основные демографические тенденции на территории муниципального образования»).

На текущий момент в системе отсутствует инструмент сбора и согласования таких пояснений: пояснения собираются вне системы, нет прослеживаемости согласования, нет архива по прошлым годам и нет единого итогового документа.

**Цель:**

Обеспечить ОМСУ, отраслевым ЦИО и куратору МЭФ инструмент сбора, согласования и архивирования пояснительных записок к муниципальному прогнозу СЭР непосредственно в системе «Конструктор форм».

**Проблема:**

Отсутствие единого инструмента сбора пояснительных записок приводит к:

- отсутствию прослеживаемости поячеечного согласования отраслевыми ЦИО;
- отсутствию архива пояснительных записок за прошлые годы;
- отсутствию единого итогового документа (выходной таблицы) по отчётному году;
- увеличению времени сбора и консолидации пояснений.

# 2. Бизнес-требования

## 2.1. Бизнес-цель

- Обеспечить сбор пояснительных данных от ОМСУ в установленные сроки;
- Обеспечить прослеживаемость поячеечного согласования отраслевыми ЦИО (включая возврат на доработку с комментарием);
- Сформировать итоговый документ пояснительной записки (выходные таблицы) за текущий отчётный год и за последние 15 лет;
- Сократить время сбора и консолидации пояснений к муниципальному прогнозу.

# 3. Бизнес-логика и сценарии проверки

## 3.1. Описание бизнес-процесса

### 3.1.1. Жизненный цикл кампании сбора

```
Не запущена (draft) ──запуск──▶ Идёт сбор (collecting) ──остановка──▶ Завершена (completed)
```

- **Запуск сбора**: статусу кампании устанавливается «идёт сбор», фиксируется время запуска, всем активным ОМСУ и ЦИО рассылается уведомление «Запущен сбор пояснительной записки». В указанную дату система автоматически рассылает уведомления и формы.
- **Остановка сбора (окончание сбора)**: статусу кампании устанавливается «завершена»; из собранных (согласованных) данных формируется выходная таблица пояснительной записки за отчётный год; повторный запуск завершённой кампании невозможен.
- Кнопка «Запустить сбор» недоступна для завершённой кампании.

### 3.1.2. Автомат состояний ячейки

**Таблица 2.** Переходы состояний ячейки:

| Исходное состояние | Действие | Итоговое состояние |
| --- | --- | --- |
| (не заполнена) | ОМСУ заполняет ячейку | Черновик |
| Черновик | ОМСУ отправляет | На согласовании у ЦИО |
| Возвращено | ОМСУ дорабатывает и отправляет снова | На согласовании у ЦИО |
| На согласовании у ЦИО | ЦИО согласовывает | Согласовано |
| На согласовании у ЦИО | ЦИО возвращает с комментарием | Возвращено на доработку |
| На согласовании у ЦИО | ОМСУ отзывает | Черновик |
| Возвращено на доработку | ЦИО отменяет возврат | На согласовании у ЦИО |
| Согласовано | ЦИО отзывает согласование | На согласовании у ЦИО |
| Любое состояние со значением | ОМСУ изменяет значение | Черновик |
| Черновик | ОМСУ очищает значение | (не заполнена) |

Схема:

```
(не заполнена)
      │ заполнение ОМСУ
      ▼
  черновик ──────────────▶ на согласовании у ЦИО ──────────▶ согласовано
      ▲    отправка              │        ▲                      │
      │                          │        │                      │ ЦИО «Отозвать»
      │ ОМСУ «Отозвать»          │        │ ЦИО «Отменить        │
      │                          ▼        │  возврат»            │
      └────────────────────── возвращено ◀┴──────────────────────┘
                         ЦИО «Вернуть» (с комментарием)

  возвращено ── ОМСУ доработка + отправка («Отправить снова») ──▶ на согласовании у ЦИО
  любое состояние со значением ── ОМСУ изменил значение ──▶ черновик
  черновик ── ОМСУ очистил значение ──▶ (не заполнена)
```

### 3.1.3. Вывод статуса шаблона

Статус шаблона по территории выводится автоматически по статусам его ячеек (приоритет сверху вниз):

| Условие | Статус шаблона |
| --- | --- |
| Нет ячеек со статусом | Не заполнен |
| Есть хотя бы одна «возвращена на доработку» | Возвращена на доработку |
| Есть хотя бы одна «на согласовании у ЦИО» | На согласовании у ЦИО |
| Все заполненные ячейки «согласованы» | Согласовано ЦИО |
| Иначе | Черновик |

### 3.1.4. Статус данных ЦИО

- все ячейки шаблона по территории согласованы → `approved`;
- ячейка возвращена → `returned`;
- согласование отозвано либо возврат отменён → `none`.

### 3.1.5. Распределение ячеек по столбцам

Ячейки строки равномерно занимают все данные столбцы: каждая ячейка занимает `floor(m/n)` столбцов, первые `m mod n` ячеек — на один столбец больше, где `m` — число столбцов, `n` — число ячеек строки. Количество ячеек строки: по умолчанию равно числу столбцов, минимум — 1, максимум — число столбцов.

### 3.1.6. Архив

Архивный год — снимок завершённой кампании за соответствующий год: отображаются все шаблоны (включая неактивные) целиком, без фильтра по показателю; данные — завершённые (согласованные) значения кампании.

## 4.4. Обработка ошибок

## 4.5. Практика TDD и контроль качества

- Модульные тесты: расчёт распределения ячеек по столбцам (colSpan), вывод статуса шаблона из статусов ячеек, вывод статуса данных ЦИО.
- Интеграционные тесты: автомат состояний ячейки (все переходы Таблицы 2), жизненный цикл кампании.
- Ручное тестирование: тестовые сценарии раздела 3.2 (17 сценариев) — 100% должно быть пройдено до передачи на приёмку.
- Код-ревью и статический анализ — в соответствии с внутренними регламентами Исполнителя.

# 5. Приложение

## Приложение А. Ограничения прототипа

1. Данные хранятся в памяти браузера (без бэкенда); демонстрационные данные генерируются при загрузке.
2. Архивные данные — детерминированные демонстрационные данные, а не фактическая историческая отчётность.
3. В прототипе остановка сбора возвращает статус «не запущена»; выставление статуса «завершена» и формирование выходной таблицы по окончанию сбора в прототипе не реализованы.
4. Компонент таблицы ПЗ предусматривает резервный вариант ячеек, не участвующих в согласовании ЦИО (например, «Наименование предприятия»); в текущих шаблонах все ячейки участвуют в согласовании.
